# Approximate-MIPS Query Stopping

## Optimization priority

Your primary objective is **PASS on every required workload and every required
metric**, with all correctness and validity requirements satisfied. The continuous
score is a secondary optimization objective; a higher score cannot compensate for
any failed PASS condition. Do not replace a solution known to satisfy all tested
PASS conditions with one known to fail them merely to increase its score.
Exploratory trials may regress; if no solution passes yet, work on the unmet
conditions and retain a valid submission as a fallback.

Successful verifier execution or a positive score does not mean scientific PASS.
Use the reported per-metric pass/fail progress to assess the tested workloads.
Train feedback covers only its evaluated workloads; passing train does not prove
final PASS. Final independently evaluates the submitted artifact on its specified
suite. The scoring formula, validity rules, and PASS comparisons below are unchanged.

## Problem
FARGO is a C++ system for approximate maximum-inner-product search (MIPS). MIPS ranks collection vectors for a query vector by their dot product; it is used in retrieval, recommendation, prediction, and other high-dimensional similarity tasks. FARGO partitions vectors by norm, indexes the partitions in locality-sensitive hash tables, and orders bucket probes globally across the tables. The evaluated input is the real Audio dataset linked by the authors' artifact README: 54,387 dense 192-dimensional `float32` vectors, exact top-100 ground truth for the first 300 vectors used as queries, and the authors' binary function table. For every evaluated query, each of three approximation ratios, and each of four result-heap capacities, the program produces up to the capacity in distinct results ordered by decreasing exact inner product; scoring uses at most the first 50. The program writes aggregate elapsed time, recall, inner-product ratios, and distinct-candidate verification counts to standard output, and all required records must be complete, finite, correctly labelled, and in range. **The secondary continuous objective is to maximize a score that combines result quality with elapsed-time and verified-candidate efficiency relative to the fixed-candidate-budget starter policy.** The authors' per-query termination condition and function-table loader have been removed; the shipped `should_stop` uses the fixed candidate budget, and you must supply the stopping decision.

## Design space
The task boundary is the existing online policy entry point `should_stop(const SearchState&)` and any supporting C++ declarations or definitions placed in `src/alg.cpp`. The policy may use the state supplied on each call, the evaluator-provided resource named by that state, and process-local state expressible within the editable file. Its required return value is a Boolean saying whether probing of the current partition ends after the bucket just processed. The `SearchState` layout, call site, query and result types, heap capacity, partition order, index, hash tables, bucket frontier, candidate verification, timers, and metric printer are fixed. The entry-point signature and all non-editable source and harness files must remain unchanged. Standard-library C++ that builds under the shipped compiler settings may be added inside `src/alg.cpp`; no other source file, dependency, generated artifact, command-line contract, or output-record contract is part of the editable surface.

## Workload
The Audio collection contains 54,387 vectors of dimension 192. The first 300 collection vectors have exact top-100 records generated by the authors' exhaustive inner-product benchmark procedure. The evaluator divides those queries into two fixed, disjoint suites of 150 queries: public suite 0 supplies development feedback, while final grading freshly reruns suite 0 and adds hidden suite 1. Each suite uses approximation ratios `c∈{0.6,0.8,0.9}`, requested result count `k=50`, five hash tables, 12 hash bits per table, and result-heap capacities `100`, `200`, `400`, and `800`. The paper evaluates `c∈{0.1,0.2,...,0.9}` and uses `0.8` by default; selecting the three-value subset is a challenge constant (not from the paper materials).

One suite process builds a deterministically seeded index and runs its 150 queries once at each of the 12 ratio/capacity combinations. For paired scoring, the evaluator separately runs the submitted, fixed-candidate-budget, and reference policies on the same suite with hash seed `314159`. Train computes each workload metric over the 150 public observations. Final pools the freshly measured public and hidden observations by matching ratio/capacity key and recomputes each workload metric over all 300 queries before scoring or reference comparison. The fixed disjoint query split is preserved; there is no separate hidden hash seed. This is a fixed real-data MIPS workload, not a collection of strings or cases to recognize.

## Interface
Implement the existing entry point in `src/alg.cpp`:

```cpp
bool should_stop(const SearchState& search_state);
```

For a partition handled by the indexed search path, the fixed query loop first consumes that partition's matching bucket in each hash table. It then calls `should_stop` once after every additional globally ordered bucket has been consumed and all previously unseen candidates in that bucket have had their exact inner products computed. Return `true` to end probing for the current partition after that bucket, or `false` to let the fixed query loop request the next bucket. The function must return a Boolean normally and within the workload timeout on every call.

`SearchState` contains the following fields:

```text
top_scores             pointer to the live result-heap inner-product array
top_score_count        number of float entries addressable through top_scores
kth_score              heap threshold tracked by the query loop; see below
frontier_score         ordering score of the non-initial bucket just consumed
probes_performed       non-initial frontier buckets consumed in this partition
candidates_verified    distinct candidates verified so far in this partition
candidate_budget       total number of vectors in this partition
remaining_frontier     5 * 2^12 - probes_performed
approximation_ratio    current value in {0.6, 0.8, 0.9}
maximum_inner_product  query norm times the partition's maximum vector norm
hash_tables            5 for this workload
policy_resource        path to the evaluator-provided binary function table
```

`top_scores` is the current heap representation, not a list sorted by result rank, and the pointer is valid for the duration of the call. `kth_score` is initialized to `-1`. If the heap was already at its configured capacity on entry to the current partition, it is initialized to the heap minimum; otherwise it becomes the current heap minimum when a later verified candidate replaces that minimum after the heap is full. Consequently, it may still be `-1` on a call where `top_score_count` has just reached the capacity.

For example, a concrete call can have:

```text
top_scores={0.77, 0.91, 0.83}, top_score_count=3, kth_score=0.77,
frontier_score=0.42, probes_performed=18, candidates_verified=231,
candidate_budget=6000, remaining_frontier=20462,
approximation_ratio=0.8, maximum_inner_product=1.14, hash_tables=5
```

Here the three values are shown in heap order. Returning `true` ends the current partition after 18 non-initial probes and 231 verified candidates; returning `false` permits the next frontier bucket to be processed.

The evaluator builds with exactly:

```text
make -j2
```

It then invokes the instrumented executable with five positional arguments and no optional flags:

```text
./fg <data-base-path> <ground-truth-path> <policy-resource-path> <suite-id> 150
```

`data-base-path` omits the `_new` suffix, which the loader appends. `ground-truth-path` names the exact-neighbor benchmark file. `policy-resource-path` is the path exposed as `policy_resource`. `suite-id` selects one of the two query suites, and `150` is the query count.

The Audio vector file is a little-endian binary file with this complete layout:

```text
uint32 bytes_per_value
uint32 vector_count
uint32 dimension
float32 vectors[vector_count][dimension]  # row-major
```

A real header and first record from the evaluated file are:

```text
bytes_per_value=4
vector_count=54387
dimension=192
vector[0][0..7]={-0.028630, -0.477196, 0.063282, -0.048360,
                 -0.029924,  0.017145, -0.012724, -0.457150}
```

The file contains 10,442,304 vector values and occupies 41,769,228 bytes including its 12-byte header. The little-endian ground-truth file has this complete layout:

```text
int32 query_count
int32 neighbors_per_query
int32 neighbor_ids[query_count][neighbors_per_query]
float32 inner_products[query_count][neighbors_per_query]
```

Its header is `query_count=300, neighbors_per_query=100`. The first real record begins:

```text
neighbor_ids[0][0..3]={7236, 23115, 13719, 23137}
inner_products[0][0..3]={6.367080, 6.347812, 6.051079, 5.948805}
```

The 7,547,112-byte `policy_resource` file is the binary function table from the upstream FARGO materials. Its little-endian layout is:

```text
float32 theta_min
float32 theta_max
float32 score_min
float32 score_max
int32   bytes_per_value
int32   row_count
int32   column_count
float32 values[column_count][row_count]  # columns stored consecutively
```

Its real header and first stored values are:

```text
theta_min=0.0, theta_max=1.5707964
score_min=0.0, score_max=12.0
bytes_per_value=4, row_count=1571, column_count=1201
values[0][0..7]={1.000000, 0.996187, 0.992387, 0.988601,
                 0.984828, 0.981068, 0.977321, 0.973587}
```

The evaluator copies this file unchanged into each workload run and passes its path as the third positional argument and as `SearchState::policy_resource`. The function has no required output associated with this file.

For each approximation-ratio and capacity pair, the program writes exactly one aggregate record to standard output:

```text
FARGO_METRIC <c> <capacity> <mean_query_ms> <recall_at_50> <mean_result_ratio> <kth_ratio> <mean_candidates>
```

For example:

```text
FARGO_METRIC 0.8 200 1.750000 0.940000 0.990000 0.980000 3400.000000
```

This denotes `c=0.8`, capacity 200, mean query time 1.75 milliseconds, recall@50 of 0.94, mean returned-to-exact inner-product ratio 0.99 over the evaluated result positions, mean last-evaluated-result ratio 0.98, and 3,400 distinct verified candidates per query. The evaluator requires exactly one record for every combination of `c∈{0.6,0.8,0.9}` and capacity in `{100,200,400,800}`, ordered first by `c` and then by capacity as listed. Every numeric field must be finite; `mean_query_ms` must be positive, `mean_candidates` must be non-negative, `recall_at_50` must be in `[0,1]`, and `kth_ratio` must be in `[0,1.01]`. `mean_result_ratio` is diagnostic feedback and is not used in the score.

Build failures, rejected patches, crashes, malformed, missing, extra, misordered, non-finite, or out-of-range metrics, policy violations, build timeouts, and workload timeouts score zero before performance is considered.

## Scoring
**As the secondary objective, maximize the score on a 0–100 scale.** For each pair `j=(c,i)` in `J={0.6,0.8,0.9}×{100,200,400,800}` and each query returning `n` results, let `m=min(n,50)`. That query's recall contribution is the size of the intersection of its first `m` returned IDs and the exact first `m` IDs, divided by 50; `R_j` is the mean contribution over the active evaluation set: 150 public queries for train and 300 freshly measured public-plus-hidden queries for final. The query's last-result ratio is its returned inner product at rank `m` divided by the exact inner product at rank `m`, or zero if `m=0`; `K_j` is the mean ratio. Let `T_j` be mean elapsed query milliseconds and `C_j` mean distinct verified candidates. Let `T_j^fixed` and `C_j^fixed` be the same measurements from the shipped fixed-candidate-budget policy over that active evaluation set. Define `clip(x,a,b)=min(max(x,a),b)`. The evaluator computes, symbol for symbol:

```text
Q_j     = sqrt(clip(R_j, 0, 1) * clip(K_j, 0, 1))
t_j     = max(0.25, T_j^fixed / max(10^-9, T_j))
w_j     = max(0.25, C_j^fixed / max(1, C_j))
E_j     = t_j^0.25 * w_j^0.75
point_j = 100 * Q_j * E_j / (1 + E_j)
score   = clip((1/12) * sum(point_j for j in J), 0, 100)
```

The capacities, lower gain floors, exponent weights, arithmetic mean, and final clipping are challenge constants (not from the paper materials). Both elapsed time and verified-candidate count contribute to every capacity's point.

PASS is separate from this continuous score. For every one of the 12 \(c, capacity\) workloads, all four comparisons must hold against the reference policy measured over the same active evaluation set: mean query time must be strictly lower, recall at 50 must be greater than or equal, mean last-result inner-product ratio must be greater than or equal, and mean distinct verified-candidate count must be less than or equal. Final recomputes each metric from the public-plus-hidden observations before comparison. PASS is the conjunction of all 48 comparisons, with no tolerance and no compensation across workloads or metrics. Final evaluation also includes heap capacities not shown in train: at each of them, for every `c`, the recall, last-result ratio and verified-candidate comparisons against the reference must also hold for PASS (the query-time comparison is not applied there), while the score formula above stays over the 12 listed pairs.

## Calibration
The supplied fixed-candidate-budget starter policy scores approximately `49.15` on the feedback suite. Independent paired measurements vary by less than 2 score points, so a repeatable change of at least 2 points is the calibration for a genuine improvement. Measurements identical to the starter give `t_j=w_j=E_j=1` and `point_j=50*Q_j`; its measured aggregate is below 50 because `Q_j` is below one at some operating points. After each development submission, the judge also reports mean recall, mean last-result ratio, query milliseconds, and verified-candidate count.
